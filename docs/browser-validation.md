## Ollama 截斷診斷修正 · 2026-11-08

- 現場查詢 Ollama 0.40.15：`qwen3.5:4b` 載入容量為 8,192，思考支援 `[false, true]`、預設 `true`。模型宣告的最大容量不等於當前載入容量。
- 同一則合成連線測試、輸出上限 8,192：服務預設思考用了 55.467 秒，輸入 1,169、輸出 7,023，合計剛好 8,192；正式答案 0 字，因 `finish_reason=length` 被拒絕。
- 相同測試只改 `reasoning_effort=none`：0.826 秒，輸入 1,171、輸出 89，八維分數、ID、逐字證據驗證通過。沒有更換模型、放寬驗證或啟動全量分析。
- 錯誤資料從 Worker 傳回測試面板，僅包含用量與字數，不包含思考原文；新增重測按鈕、Ollama 新設定預設關閉思考，以及測試串流階段／耗時。
- `npm test` 31 項通過；生產建置及 Pages 資產檢查通過。

思考設定與實際容量依 [Ollama 相容 API 文件](https://docs.ollama.com/api/openai-compatibility) 與 [thinking metadata 文件](https://docs.ollama.com/capabilities/thinking) 核對。

- 保留中途失敗：僅關閉思考的一次瀏覽器重測仍遇到證據格式錯誤；另一個合成回覆有 null 卻未附不確定旗標，均未當成有效結果。
- 為此補充輸出結構範例與逐字證據／null 旗標要求，提示詞版本 `json-contract-v2`；Ollama 預設隨機程度 0，既有任務仍保留原提示詞及設定。
- 修改後固定的三則合成案例（感謝、普通陳述、引用辱罵）全部通過格式及證據驗證，耗時約 1.1、0.8、5.2 秒。這是輸出契約檢查，不是人工標註的準確率驗收。
- 最終瀏覽器驗證：以 256 輸出額度觸發截斷，面板顯示實際用量與字數；按「關閉思考並重測」後設定為 none / temperature 0，約 1.0 秒通過，輸入 1,385、輸出 91。未儲存測試草稿，未更動使用者既有設定。

## 實際語料驗收與證據修正 · 2026-11-08

使用者要求測到可用後，改用本機現有 `qwen3.5:4b` 與真實群聊驗收。所有輸入只送到本機 Ollama；舊 SQLite 以唯讀開啟，原網頁分析紀錄未修改。以下不是人工標註準確率。

### 重現與修正

- 原逐字引文格式在前 20 則真實可讀訊息中，16 則成功、4 則因模型在引文內插入空白而失敗，約 21.7 秒。保留失敗紀錄，沒有以去除空白或放寬驗證接受它們。
- 新版 `evidence-references-v3` 將原文分段並編號，模型只選編號，程式取回原始文字；原訊息 ID、引用邊界、目標歸屬與逐字驗證保留。上下文放前面，待評分目標放最後，降低模型誤評鄰近訊息的情況。評分規則不變，提示詞與輸入格式有變，不能宣稱分數與舊版等價。
- 單批驗證失敗最多修正重試 2 次；仍失敗保留原始錯誤與空分數，繼續後續訊息。連續 5 批失敗或服務設定錯誤才暫停。
- 修正縮小批次時的游標錯誤：候選中夾雜不可讀媒體，原本可能跳過待分析訊息並卡住；現在回到下一則未選目標的確切位置。
- 新增失敗／容量不足清單，可開啟原文、上下文與八維覆核；舊紀錄提示需要建立新分析才能使用新協定。

### 大檔與固定樣本

完整匯入目前檔案共 298,966 則（約 227 MB），430 位非系統發言者、38,121 則可精確連回原文的回覆；系統 11,602、可讀 216,471、不可讀 70,893，無無效／重複訊息、無缺失回覆。這份新檔案的數量不同於最初計畫中的舊檔案，未修改資料湊數。

固定 300 則：前 40 則可讀訊息，加上種子 20261108 的 260 則分層抽樣，依月份、訊息類型、發言者活躍程度組成 115 個層。驗收使用完整匯入資料提供鄰近上下文與回覆祖先，僅限制目標集合；不縮減上下文來源。

| 驗收階段 | 成功 | 失敗 | 容量不足 | 總耗時 |
| --- | ---: | ---: | ---: | ---: |
| 新證據格式，8K／輸出 2048 | 275 | 0 | 25 | 210.6 秒 |
| 同組 300 則，16K／輸出 2048，調整輸入順序前 | 297 | 3 | 0 | 251.9 秒 |
| 最終版，同組 300 則，16K／輸出 2048 | **300** | **0** | **0** | **254.0 秒** |

8K 的 25 則超過保守 UTF-8 位元組預算，沒有送出或截斷。16K 使用現有權重建立 `qwen3.5:4b-corpus-16k`，沒有下載權重或覆蓋原模型。第二輪的 3 則因模型誤用鄰近訊息作為正分證據而被拒收；輸入順序修正後，單獨重現這 3 則全部通過，再重跑完整 300 則驗證。

中途一次驗收腳本在重新建立引擎後未等待 `ready`，已保存 25 則後出錯；只修正驗收腳本的初始化順序，保留當次失敗摘要。後續跑次均檢查暫停、重建引擎、讀回結果及續跑；不是重置已完成結果重算。

本機私有驗收檔案位於忽略的 `.data/`：`baseline-*`、`real-qa-*`、`qa-targets.json`。不包含在 Pages 發佈內容。完整模型分析與人工語意校準仍由使用者後續執行。

### 真實瀏覽器流程

最終 `dist/` 由獨立靜態預覽來源 `127.0.0.1:5180` 提供，瀏覽器直接連 Ollama，未使用 Python。匯入目前資料中的前 50 則非系統訊息：

- 50 則、8 位成員；38 則可讀全部成功，12 則不可讀媒體跳過，0 失敗、0 容量不足。
- 模型輸出時介面顯示接收字數、經過時間與目標／上下文數量。成功 8 則時點暫停，約 390 ms 顯示已暫停；處理中歸零，8 則保留，續跑完成 38 則。
- 故意使用 4096／輸出 2048 的不足預算，38 則均顯示容量不足且未發出模型請求；清單可開啟原文／上下文及 8 個覆核欄位。這個測試獨立保存，未混入成功紀錄。
- 重新整理後從已存資料開啟，38 則完成結果與日誌保留；納入樣本不足者後可查看成員排行、完整個人頁、代表訊息與原文證據。
- 實際下載逐則 JSONL，共 50 列、50 個唯一訊息 ID；38 done、12 unknown，逐條核對匯出證據均為對應原文子字串，原始 ID 未被短編號取代。沒有為驗收改寫任何人工分數。
- 最終流程無瀏覽器 console error／warning。截圖保存在忽略的 `output/corpus-real-acceptance.png`。
- 曾誤取前 50 則原始紀錄作為 UI 測試檔，該段全為系統訊息，因此 0 個評分目標；改取前 50 則非系統訊息後才執行上述正式 UI 驗收，未將空跑當成功。
