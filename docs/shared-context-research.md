# 共享上下文與單 token 評分實測

2026-11-09。這次原型沒有達到加速目標，保留為獨立研究，不接入正式分析。216,471 則可讀訊息要在兩小時內完成，需要至少 30.07 則／秒；一小時需要 60.13 則／秒。

## 原型

使用通用模型、現有八維準則與原有上下文規則，沒有訓練專用分類器。每批建立共同提示詞和聊天資料，對每則訊息的每個維度分別提出單選題，生成一個 `0 / 1 / 2 / 3 / ?` token。`?` 還原成 `null`。服務重用共同前綴，六路並行，每路固定 slot。之後另一次生成原文證據、理由及不確定標記，使用正式程式的驗證器驗證完整結果。

研究程式：

- `scripts/research/shared-context.mjs`：分支評分、合併、證據生成、驗證。
- `scripts/research/benchmark-shared-context.mjs`：資料正規化、固定樣本、隔離服務、對照測試。
- `tests/shared-context-research.test.js`：漏項、重複、歸屬、未知、輸入截斷、證據衝突及並行錯誤保留。
- [數值紀錄](shared-context-results.json)：不含原文或成員 ID 的測試結果。

實作使用 llama.cpp `/apply-template`、`/tokenize`、`/completion` 的 grammar 與 `cache_prompt`，詳見[官方 server 文件](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)。這次沒有執行 vLLM 的 generative scoring 或 SGLang，結果只代表下面的實際組合。

## 完整流程結果

「有效則／秒」只計通過八維、ID、原文證據和未知標記驗證的訊息；請求成功與單 token 格式正確不等於完整結果成功。

| 流程 | 時間 | 完整有效 | 失敗 | 有效則／秒 |
| --- | ---: | ---: | ---: | ---: |
| 現有 JSON 流程，ub512 | 37.63 秒 | 144 | 0 | 3.83 |
| 現有 JSON 流程，ub64 | 42.14 秒 | 144 | 0 | 3.42 |
| 分支 v1，ub64，未加回答前綴 | 171.07 秒 | 8 | 136 | 0.047 |
| 分支 v2，ub64，回答前綴「分數：」 | 164.20 秒 | 128 | 16 | 0.780 |

v2 僅產生八維分數也花了 128.82 秒，即 1.12 則／秒；補證據及理由另花 35.38 秒。兩個批次因為 `null` 沒有附不確定標記而失敗，總共 16 則沒有完整結果。沒有把失敗轉為零分，也沒有排除失敗請求耗時。

## 快取有命中，但仍重算太多

v2 發出 1,152 個評分請求，產生 1,152 個分數 token。分支評分的邏輯輸入總量 3,886,352 token；服務回報實際評估 435,806 token，約 88.79% 輸入獲得重用。

現有 JSON 流程只用 66,500 輸入 token。即使命中快取，分支仍評估約 6.55 倍輸入，還未計入第二階段證據生成。每個 slot 首次載入上下文、分支尾部重算及大量小請求累積的成本，超過了減少輸出 token 帶來的收益。

這個 Qwen 混合架構在所測 llama.cpp 版本中不支援 partial sequence removal，服務使用 recurrent-state checkpoints。合成探測中，ub512 重複分支仍評估約 516 token；ub64 可降至約 68 token。這是選用 ub64 的理由，但它仍不足以改善端到端速度。

數值紀錄中的輸出 token 加總只包含成功回應；被驗證拒絕的回應和重試可能消耗額外 token，因此不把它當成完整用量或費用。

## 答案前綴影響與評分差異

v1 的 1,152 個單選判定中，有 962 個未知。對第一批 64 個判定另做診斷：

| 設定 | 未知 | 時間 |
| --- | ---: | ---: |
| 無回答前綴、關閉快取、限制單 token | 56/64 | 52.18 秒 |
| 加「分數：」前綴、開啟快取、限制單 token | 1/64 | 3.03 秒 |
| 無回答前綴、開啟快取、不限制 grammar，最多 32 token | 56/64 | 3.24 秒 |

第三組另有一個非單字元回覆。這些對照顯示回答前綴敏感性，不能只歸因於 grammar，也不能把未知減少當成準確率提高。診斷組之間有快取狀態與順序差異，時間僅供排查；完整流程速度以 144 則實測為準。

v2 最後有兩個未知判定。對照 ub64 JSON 流程，在 128 則雙方皆有完整結果的訊息中，資訊貢獻只有 64 則分數完全相同，平均差 0.98 分（0–3 尺度）；建設性討論 79 則相同，平均差 0.66 分。這是兩種提示流程的差異，不是人工標註準確率。完整各維度數值見 JSON 紀錄。

目前分支提示詞沿用原始八維提示後追加單維要求，仍有格式要求重疊；證據階段也有補寫理由的偏差風險。更換評分架構需重新做人工校準，不能因為通過 JSON 驗證就宣稱與原流程等效。

## 重現

準備已存在的 llama-server、GGUF、QCE 聊天 JSON；在專案根目錄執行，將三個路徑改成自己的檔案：

```powershell
node scripts/research/benchmark-shared-context.mjs `
  --server=C:/llama/llama-server.exe `
  --model=C:/Models/model.gguf `
  --source=.data/chat.json `
  --out=.data/shared-context-run `
  --ubatch=64 `
  --phases=baseline,branches
```

端口 11439 需空閒。輸出目錄保存完整結果及 server.log；其中可能有聊天原文與 ID，位於已忽略的 `.data/`。只重測診斷時使用 `--phases=diagnostic`。對照不同組結果可用 `--baseline=.data/另一組/baseline.jsonl`。

本次原始資料保留於 `.data/branch-research-512/`、`.data/branch-baseline-64/`、`.data/branch-research-64/`、`.data/branch-diagnostic/`、`.data/branch-research-v2/`。v1 首次 summary 的訊息成功數曾被維度判定數覆蓋，已從 JSONL 還原為 `summary-corrected.json`，原始檔仍保留；本文使用修正後的 8 成功／136 失敗。

結論：不採用這個「每則八次 HTTP 分支、再補證據」實作。後續若測服務內部批次 scoring，須先證明能在一次排程中處理多個分支，並連同證據生成與人工校準一起驗收。現有數據不支持一至兩小時的完成承諾。
